## 3. 正式清单

### 3.1 P1 · v4 三十套（仅重画 270 张）

**现状 `[数据]`**

- `public/sprites/v4/` 共 1140 张 = 30 套 × 38 张
- 每套构成：icon ×4 + 普攻（start 4 / mid 4 / main 6 = 14）+ 神通（start 4 / mid 8 / main 8 = 20）
- 生成器 `scripts/generate-v4-assets.mjs`（844 行，纯 Node 手写 PNG 像素 + zlib deflate），**零手绘**
- 均值 2,397 字节，尺寸 32×32 ~ 64×64
- 对照真实美术：`beast_bear_sheet.png` 2048×2048 / 2.66 MB，`city_bg.png` 1445×2060 / 5.31 MB

**关键结论：`1140 张是"零渲染负债"` `[数据]`**

| 核查项 | 结果 |
|---|---|
| `src/v4/` 内 `add.image` / `add.sprite` / `make.sprite` / `this.textures` | **0 命中** |
| `scene-adapter.ts`（311 行）渲染方式 | 100% `scene.add.graphics()` |
| `manifest.ts` 的 `availableFrames` / `frameTextureExists` / `missingFrames` | src 内**无人调用**（仅 tests 引用） |
| `BootScene.ts:387-398` | 对全 30 套逐张 `load.image` = **1140 个纹理** |

→ 1140 张全部被加载，**0 张被渲染**。战斗表现完全由 Graphics 图元实时绘制。

**因此评估维度必须改变**：先回答"接不接进渲染管线"，再谈"画得好不好"。原"1140 张全量重画（34–48 人天）"的口径**已作废**。

**路线 A（推荐）`[美术]`**

| 内容 | 数量 | 说明 |
|---|---|---|
| 装备图标 | 30 张（每套 1 张） | 玩家感知最强 |
| 神通 main 帧 | 240 张（30 套 × 8） | 大招表现 |
| **合计** | **270 张** | 其余 870 张保留 Graphics 兜底 |

- 配套：30 张 per-kit atlas，请求数 1140 → 30
- 分批：K01–06 做风格模板 → K07–18 → K19–30 派生
- **硬性约束**：现有 32/64px 几何占位图一旦接进渲染，观感会比 Graphics 图元**更差**（平滑图元 → 粗糙色块）。接渲染必须绑定"只放已重画的 270 张"，**禁止出现"先全量渲染占位图、后面再慢慢替换"的中间态**。

**有利证据 `[数据]`**：灰度归一化跨套平均差异 **25.33**。形状确实不同，不是"同一张图换配色"。最像的起手帧 10.41（`atk_start_1`），最不像的收尾帧 41.56（`art_main_8`）。

**不利证据 `[数据]`**：25/30 套的 4 张 icon **字节完全相同** → 图标静止不动。有差异的仅 k04 / k10 / k11 / k12 / k28。

**事实记录 `[数据]`**

28 张 PNG 内嵌 tEXt 元数据：

```json
  "os":"web","product":"commercepro_app","videoId":"",
  "pictureId":"5204711372044","editType":"integrated_agent",
  "appVersion":"","threadid":"06f04db5-4154-4132-bf61-be23fbb9b00f"}}
```

| 批次 | 时间 | 张数 | threadid |
|---|---|---|---|
| 1 | 2026-08-22 19:30 | 22（ring 8 + splash 8 + spark 6） | `06f04db5-…` |

- 28 个 `pictureId` 全唯一
- `scripts/` 内对这四组**零命中**（对比自研组命中 `generate-fx-assets.mjs`）→ 人工下载后手动放入
- **项目内无任何文件名含 douyin / 抖音的文件**——douyin 仅存在于内嵌元数据

**真实用量 `[数据]`**（经 `DungeonScene.burstFx()` 封装调用，非直接 `.play()`）

| 组 | `burstFx()` 调用 | 饱和度 | 状态 |
|---|---|---|---|
| `fx_ring` | 11 处 | 0.168 | 在屏，中性灰基底 |
| `fx_splash` | 9 处 | 0.185 | 在屏，中性灰基底 |
| `fx_spark` | 8 处 | 0.058 | 在屏，中性灰基底 |
| `mod_blade` | **0 处** | 0.465 | 死资源（仅 `DungeonScene.ts:1993` 注释提及） |

**设计澄清**：前三组是**低饱和灰度基底**，`burstFx` 内部执行 `s.setTint(...)` 上色（调用处传 `0xd8f0ff` 淡蓝 / `0xb39dff` 紫 / `0xffe9a8` 金等）。**低饱和基底 + setTint 是标准做法，设计意图正确**，不可按"AI 图违和"误删。

**用户裁定**：来源无问题，**继续沿用**。不删除、不替换、不重画。合规项关闭，省下 1–2 人天。

**遗留提示**：28 个 `pictureId` + 2 个 `threadid` 会随 `dist/` 发布，理论上可被追溯。如需降险可写脚本剥离 PNG 的 tEXt 块（不改像素，约 5 分钟）。**未获指示，暂不执行。**

### 5.1 Kit 机制重复 —— 所有 v4 美术的前置

**问题** `[数据]`：30 套只有 **28 种唯一「普攻/神通」组合**。

```
回旋/雷桩  →  k02 旋刃套  ≡  k26 旋桩套
往返/回旋  →  k03 飞旋套  ≡  k09 往旋套
```

**为何必须先解决**：用户在设计裁定中明确要求"30 套必须全部拥有独立的普攻和神通机制，不共享核心行为"。这两套的美术做得再不一样，**行为上仍是同一套**。一旦 270 张接进渲染管线，差异即被固化，再改数据等于美术返工。

**待研究**：
- k02/k26 与 k03/k09 各改用哪两个原语组合，才能保证 30 组全唯一
- 改动是否影响已生成存档中的套装（`saveVersion` / schema 兼容性）
- 是否连带调整原语分布（见 5.2）

**状态**：⏸ 待用户批准修改 `src/data/v4-kits.json`
