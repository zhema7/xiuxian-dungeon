### 0.3 术语

- **动态套装／PRS 记录**：由确定性种子生成并持久化的随机套装记录。
- **生成器 v2**：本轮新生成逻辑的版本标识，写入 `generation.generatorVersion = 2`；不等同全局 `SAVE_VERSION`。
- **schema v3**：本轮新生成动态记录的记录级 schema 标识，写入 `schemaVersion = 3`。
- **攻击通道**：决定普通攻击模式、攻击名称、攻击行为说明、攻击联动与攻击阶段 VFX 的能力通道。
- **神通通道**：决定套装神通模式、神通名称、倍率、基础冷却、神通行为说明与神通阶段 VFX 的能力通道。
- **首个有效命中**：战斗逻辑确认目标存活、碰撞成立并实际进入伤害结算的首个命中事件；挥空、撞墙、预测碰撞、纯 VFX 回调、子体命中均不算父源首中。
- **同源**：同一个胜出的攻击／神通能力记录及其明确归属的真实事件对象；不以颜色、坐标接近或时间相近猜测来源。
- **预留**：可被 schema／resolver 的边界测试识别，但本轮生成器、掉落、UI 与玩家内容均不得产生或展示。

# 第一节｜概述

## 1.1 设计目标与体验支柱

### 设计支柱

1. **可复现的造化身份**：同一 `seed + sequence + existingCatalog` 产生同一份完整语义结果；玩家获得的是一套稳定、可收藏、不会读档变形的装备身份。
2. **可理解的 Build 取舍**：2 件提供清晰数值方向，4 件改变攻击／神通通道；不同 `setId` 的数值可以并存，但能力不会无边界互相串联。
3. **受控的命中惊喜**：首中联动提供有限的“命中后再演化”反馈；联动自动、短促、可测试，不破坏竖屏单手的输入支柱。

### MDA 校验

| 层级 | v3 落点 | 设计红线 |
|---|---|---|
| **机制 Mechanics** | 有限 8 profile、确定性生成、2/4/6 阶梯分流、两条首中配方、六槽边界。 | 不把文本变成可执行 DSL；不让 VFX 自行生成伤害；不让 `dageng` 获得额外联动。 |
| **动态 Dynamics** | 玩家在“补齐某套的 4 件能力”和“用其他套的 2 件数值补 Build”之间取舍；攻击／神通可在混穿时分别来自不同来源。 | 不允许所有强词、所有联动、所有高覆盖神通同层叠满。 |
| **美学 Aesthetics** | “天机推演、术式首中演化、四件成形”的发现感。 | 诗性名称不能暗示冻结、领域、额外爆炸或未实现控制。 |

### 玩家心理映射

- **探索者**：通过 seed、套名、招式名与神通名形成收藏差异。
- **成就者**：追求补齐 4 件并验证真实攻击／神通路线。
- **建造者**：利用多 `setId` 的独立 2 件数值，构造数值与能力分流的组合。
- **社交／比较需求**：比较的是可复述的事实句与路线，不是内部 ID 或无法重现的随机画面。

## 1.2 本期范围（In Scope）

### 生成与数据

- 新生成动态记录使用 `schemaVersion = 3`、`generatorVersion = 2`。
- 每套随机套装固定生成 4 个基座与 4 个 `pieces`：`weapon`、`head`、`armor`、`boots`。
- 继续从已登记的 8 条 profile 中选择攻击模式、神通模式、固定神通倍率／冷却与四条正式 `vfxRecipe`。
- 生成确定性主题、部件中文名、招式中文名、神通中文名、2/4 件数值与中文事实说明。
- 生成有限的攻击通道联动配方：飞剑首中分裂或巨剑首中火弹；不生成其他联动。

### 运行时语义

- 多 `setId` 数值阶梯按各自有效件数独立聚合。
- 2 件只进入数值聚合；4／6 件能力按攻击／神通／特效三路合同解析，其中特效只做同源表现合并。
- `vfxRecipe`、`fxTags` 与其胜出能力保持同源；禁止从低优先级套装借视觉或联动。
- 联动由已有攻击命中事件自动触发；不新增主动输入。
- 未知槽位不计件、不生效、不进入数值、路由、VFX 或联动。

### 兼容与验收

- 读取 schema v2 与无 schema 的 legacy 动态记录。
- 旧记录保持已落盘的模式、数值、名称与标签语义；不得用新词池重新抽取。
- 为 schema v3、通道分流、联动冷却、六槽边界与静态套回归提供可执行验收项。

## 1.3 明确非目标（Out of Scope）

本轮不得把下列内容写入新随机结果、掉落池、玩家 UI 或 schema v3 的可玩承诺：

# 第二节｜机制：生成、能力分流与受控配方

## 2.1 生成器 v2 流水线

生成器的输入、顺序和失败策略必须稳定：

1. **读取目录**：读取当前动态套装目录、静态保护 ID、已占用 `set_dyN` 序号与主题使用情况。
2. **容量判断**：沿用当前动态套装上限／补齐策略；达到上限时优先补已有套装部件，不创建新记录。上限的具体数值沿用当前工程配置，除非另行审批。
3. **取得输入 seed**：由调用方提供 32 位无符号 `seed`；生成路径只消费注入 RNG，不调用 `Math.random`、`Date.now` 或隐式全局随机。
4. **分配 sequence**：选择最小未占用的正整数序号，生成 `set_dyN` 与四个基座 ID；不能覆盖稀疏旧记录。
5. **选择 profile**：从 enabled 的 8 条 profile 中按注册权重选择；候选为空时显式失败，不默认回退为飞剑。
6. **选择主题与名称**：按 profile 允许主题确定性选取套名、四件部件名、攻击名与神通名；主题池耗尽时使用确定性后缀，不静默复用同名。
7. **生成数值层**：2 件与 4 件只从已登记 `Mods` 池／预算表取值；数值层与能力层分开生成。
8. **生成能力通道**：把 profile 的攻击字段写入攻击通道，把神通字段写入神通通道；不得把攻击字段写进神通通道或反之。
9. **选择联动配方**：仅当攻击通道胜出源的攻击模式、神通通道胜出源的神通模式与禁配条件全部满足时，选择一条首中配方；神通通道为 `dageng` 一律选择 `none`。若两个通道来自不同 `setId`，不得读取攻击源附带的旧 `artMode` 代替神通通道胜出源。
10. **绑定同源 VFX**：为攻击通道与神通通道绑定已兼容的正式 recipe；联动不新增 recipe。
11. **物化四件**：只生成武器、头部、衣甲、靴子四个基座；不得在生成器内创建 `charm1`／`charm2` 部件。
12. **交叉校验**：校验 `set ↔ bases ↔ pieces ↔ generation ↔ profile ↔ channels ↔ recipe` 的一致性；失败则整条候选失败，不部分修补。
13. **完整落盘**：写入 schema v3、generator v2、seed、sequence、完整 `set`、完整 `bases` 与审计元数据。读取时以落盘结果为权威，不重掷。

### 确定性要求

- `existingCatalog` 是输入的一部分；目录不同导致主题或 profile 不同属于可预期差异。
- 生产／掉落调用必须先取得显式 `seed`，再调用等价于 `genDynamicSetFromSeed(seed, sequence, existingCatalog)` 的入口；生成器本身不得在缺省 seed 时暗中补用时钟或全局随机。GM／测试入口也必须记录输入 seed。
- 同一 `seed + sequence + existingCatalog` 的语义快照必须深度相等；实例 UID 若由装备实例系统另行生成，不属于生成语义比较范围。
- RNG 消费顺序必须固定；注册、解析、VFX 播放不得偷偷消费生成 RNG。
- 生成失败必须有可诊断原因：无 profile、主题无归属、ID 冲突、预算无可用项或 recipe 不兼容均不得静默生成默认内容。

## 2.2 能力分流合同：攻击通道／神通通道／特效通道

### 逻辑结构

每个 4／6 件能力行可包含数值 `mods`，以及一个或两个彼此独立的能力通道：

```ts
// 设计语义合同；字段名可由工程映射，但所有权与行为不可改变。
type LinkageRecipeId =
  'none'
  | 'flying_sword_first_hit_split'
  | 'giant_sword_first_hit_fire_bolt'

type ControlledHitLinkageV3 =
  | {
      recipeId: 'flying_sword_first_hit_split'
      parameters: {
        childCount: 2
        damageMultiplier: 0.4
        cooldownMs: 800
        nonRecursive: true
      }
    }
  | {
      recipeId: 'giant_sword_first_hit_fire_bolt'
      parameters: {
        projectileCount: 1
        damageMultiplier: 0.4
        cooldownMs: 1200
        nonRecursive: true
      }
    }

interface SetBonusV3 {
  count: 2 | 4 | 6
  mods?: Partial<Mods>
  attack?: {
    mode: DynamicAttackMode
    name: string
    behavior: string
    transformId?: string
    linkage?: LinkageRecipeId
    vfxRecipe?: ProceduralVfxRecipe
    fxTags?: string[]
  }
  art?: {
    mode: ArtMode
    name: string
    behavior: string
    power: number
    cooldownMs: number
    vfxRecipe?: ProceduralVfxRecipe
    fxTags?: string[]
  }
  desc: string
}
```

### 与当前源码字段的精确映射

当前 `src/data.ts` 的生产类型仍是扁平 `SetBonus`，因此本 GDD 的嵌套结构是**语义视图**，不是要求本轮新增一套平行字面 schema。规范化／解析适配必须保持以下一一映射：

| 语义通道 | 当前扁平字段 | 允许携带的内容 |
|---|---|---|
| 攻击通道 | `attackMode`、`attackName`、`transformId`、与攻击来源绑定的 `hitLinkage` | 普通攻击模式、名称、行为、攻击联动资格；不得读取 `artMode` 作为攻击能力。 |
| 神通通道 | `artMode`、`artName`、`artPower`、`artCooldownMs` | 神通模式、名称、倍率与基础冷却；不得从攻击字段推导神通。 |
| 特效通道 | `vfxRecipe`、`fxTags`，按当前胜出来源携带 | 只作同源表现消费；不得独立成为伤害、输入、目标或生命周期能力。 |
| v3 生成审计 | `generation.move`、`generation.art`、`generation.vfxRecipe`、`generation.identity`、`generation.hitLinkage` | `move` 是攻击语义，`art` 是神通语义；`identity` 与 `hitLinkage` 必须和 `set.bonuses` 交叉一致。 |

当前生成器的 4 件 bonus 使用 `attackMode`／`artMode`／`attackName`／`artName`／`vfxRecipe`／`hitLinkage`／`artPower`／`artCooldownMs` 的扁平组合；因此“攻击／神通独立”首先表示**解析所有权独立**，不要求把一个 profile 拆成两个随机 profile，也不授权把 `generation.attack` 写入当前生产记录。若未来工程改成嵌套存储，必须提供与上述扁平记录的无损往返适配。

实现若继续使用现有扁平字段，必须在规范化层得到完全等价的通道视图：`attackMode/attackName/transformId` 只能归入攻击通道，`artMode/artName/artPower/artCooldownMs` 只能归入神通通道；`hitLinkage` 只能在通过 `isControlledHitLinkageCompatible()` 的攻击来源上生效；不能因字段扁平而恢复“整条 bonus 一个不可分的隐式能力源”。

### 件数规则

| 件数 | 数值 `mods` | 攻击通道 | 神通通道 | 特效通道 | 新随机内容 |
|---:|---|---|---|---|---|
| 2 | 可有；只参与数值聚合 | **禁止** | **禁止** | **禁止** | 生成器会写 2 件数值行。 |
| 4 | 可有；参与数值聚合 | 可有；当前随机套装的主攻击能力 | 可有；当前随机套装的主神通能力 | 只能引用对应胜出能力的 recipe／标签／联动表现，不独立造机制 | 生成器写入；能力可玩验收对象。 |
| 6 | 可有；参与数值聚合 | 合同允许 | 合同允许 | 只能从同源攻击／神通能力合并 | 仅预留／夹具边界；本轮生成器不写。 |
| 其他 | 不合法 | 不合法 | 不合法 | 不合法 | 整条记录拒绝或隔离。 |

### 三路通道所有权

- **攻击通道**拥有普通攻击模式、攻击中文名、攻击行为句、攻击联动资格与攻击阶段 recipe。
- **神通通道**拥有套装神通模式、神通中文名、神通行为句、`power`、基础 `cooldownMs` 与神通阶段 recipe。
- **特效通道**不是第三种伤害或输入能力，而是表现合并视图：只能消费攻击／神通通道已经胜出的 `vfxRecipe`、`fxTags` 与真实联动对象；它不拥有独立目标、倍率、冷却、资源、生命周期或触发器。
- 攻击与神通来自不同 `setId` 时，特效通道输出两个带来源的同源表现包（攻击表现包、神通表现包），不得把两个 recipe 任意拼成第三条新 recipe。
- 同一通道重复标签先去重；不同通道只有在标签注册表明确允许合并时才可并存，冲突必须拒绝或稳定抑制并留诊断。

### 通道解析顺序

对攻击通道、神通通道分别执行以下步骤，不共享胜出结果：

1. 收集所有已知六槽中、属于同一 `setId` 且达到自身 `count` 门槛的能力行。
2. 只保留本通道拥有字段的行；另一通道字段不会被借用。
3. 按 `count` 降序选择高阶能力；同件数按稳定的 `setId` 码点字典序打破平局，不依赖装备对象遍历顺序。
4. 将该通道的模式、名称、数值、联动资格、recipe 与通道标签作为一个同源包一起输出。
5. 没有胜出能力时，该通道回退到原有主修招式／职业默认（攻击）或玩家已装配神通（神通）；不得从另一通道拼接字段。

因此，允许出现如下合法混穿：A 套的 4 件攻击能力 + B 套的 4 件神通能力 + A/B 各自的 2 件数值。此时攻击 VFX 只能来自 A 的胜出攻击能力，神通 VFX 只能来自 B 的胜出神通能力；任何一方不得借用另一方的 recipe、联动或标签。

## 2.3 受控命中联动机制配方

联动是**有限目录**，不是可执行字符串。当前首批只登记以下两条；未列出的攻击家族、神通家族与标签均视为 `none`。

|---|---|---|---|---|---|---:|---|---|
| `flying_sword_first_hit_split` | 攻击 | `flying_sword_burst` | 神通不得为 `dageng` | 同一父飞剑的首个有效命中；每个父体最多申请一次，且共享来源冷却可用 | 产生 2 把子剑；每把按父投射物有效倍率 `×0.4` 进入既有伤害管线 | `800 ms` | `false` | 自动触发；不加按钮。表现复用 `sword-comet` 的剑形／命中锚点。 |

### 联动统一规则

- **首中定义**：只有实际进入伤害结算的有效命中才占用首中资格；挥空、撞墙、超出生命周期、仅播放 VFX、命中已死亡目标均不触发。
- **来源冷却**：冷却按胜出的攻击能力来源维护；飞剑为 `800 ms`、巨剑为 `1200 ms`，以整数毫秒比较，达到或超过冷却边界才可再次触发。它是机制内置冷却，不是神通基础冷却；本合同不允许 `artCooldownMs` 或 `cdPct` 隐式重写它。若换装导致攻击或神通胜出源变化，旧来源的冷却／首中资格必须失效并清理；新来源从当前场景时钟的可用状态开始，不能继承另一来源的剩余冷却。
- **同帧排序**：同一时间戳有多个候选首中时，以战斗逻辑提供的攻击事件序号／投射物创建序号裁定唯一先后；不得用坐标或数组偶然顺序猜测。
- **子体封锁**：两把子剑、追加火弹及其后续命中不是父源，不能再次申请同类联动；不得递归、反弹、链式扩张或跨目标补造规则。
- **目标与轨迹**：子剑／火弹的目标、朝向、碰撞体、生命周期和销毁由战斗逻辑决定；本合同只增加已批准的数量、倍率、触发与冷却，不发明额外索敌或范围规则。
- **大庚硬禁配**：只要胜出神通通道为 `dageng`，攻击联动字段必须解析为 `none`；若存档伪造联动，v3 校验拒绝，新运行时安全关闭，不能由攻击模式单独推断恢复。
- **自动化**：联动没有独立按钮、独立资源、独立瞄准线、独立手动确认或第三个 HUD 操作入口；玩家只使用既有攻击键与神通键。
- **VFX 不反向造物**：VFX 只能消费战斗逻辑已创建的子剑／火弹对象，不能创建投射物、设置倍率、选择目标、调用命中、补发伤害或以爆点冒充真实火弹。

# 第三节｜数据、命名、标签与视觉契约

## 3.1 schema v3 记录合同

以下先列出**当前生产记录的字面形状**，再说明它如何投影成 2.2 的攻击／神通／特效语义视图。字段名可由工程适配，但不得改变字段归属、数量、版本与交叉验证关系。

```ts
// 当前 src/lore.ts / src/data.ts 的持久化语义（SetBonus 保持扁平）。
interface DynamicSetRecordV3 {
  schemaVersion: 3
  generation: {
    generatorVersion: 2
    seed: number              // uint32，0..0xffffffff
    sequence: number          // 正整数；对应 set_dyN
    theme: string
    profileId: string         // 8 条已登记 profile 之一
    move: {                   // 攻击通道审计副本；不是 generation.attack
      id: string
      name: string
      mode: DynamicAttackMode
      behavior: string
    }
    art: {                    // 神通通道审计副本
      id: string
      name: string
      mode: ArtMode
      behavior: string
    }
    vfxRecipe: ProceduralVfxRecipe // profile 级 recipe；须同时通过 attack/art 兼容校验
    identity: {
      setId: string
      profileId: string
      transformId: string
    }
    hitLinkage: ControlledHitLinkageV3 | null
  }
  set: {
    id: string
    name: string
    pieces: [string, string, string, string] // 只对应 weapon/head/armor/boots
    bonuses: [SetBonus, SetBonus]            // 当前生成结果固定 2 件 + 4 件；实际为扁平字段
  }
  bases: [ItemBase, ItemBase, ItemBase, ItemBase]
}
```

`generation.move`、`generation.art`、`generation.identity` 与 `generation.hitLinkage` 是当前 v3 的审计／严格校验字段；`set.bonuses` 中的 4 件扁平行是运行时能力与玩家说明的主要来源。2.2 的 `SetBonusV3.attack`／`art` 只是归一化后的通道包，不是要求本轮额外持久化的 `generation.attack` 字段。

### 权威与重复字段

- `set` 与 `bases` 是运行时装备与读档的权威副本；`generation` 是审计、重放与交叉校验副本。
- `generation.move` 必须与 4 件行的 `attackMode`／`attackName`／行为语义一致；`generation.art` 必须与 `artMode`／`artName`／`artPower`／`artCooldownMs` 的 profile 语义一致。
- `generation.identity` 必须回指 `set.id`、`profileId` 与 4 件行的 `transformId`；`generation.hitLinkage` 必须与 profile、攻击模式以及**神通通道胜出源的 `artMode`**共同通过 `isControlledHitLinkageCompatible()`，并与 4 件行的 `hitLinkage` 同值或按无联动规则为 `null`／缺省；不能只凭攻击模式恢复联动。
- 任何 `generation` 与 `set.bonuses` 不一致的 schema v3 记录整条隔离，不按当前词库修复、不重掷。
- 新生成记录不得写入 6 件 bonus、6 个随机基座、饰品基座、掉落字段或 UI 字段。
- v3 新记录的 `pieces` 顺序固定为 `weapon → head → armor → boots`；顺序变化必须由规范化层显式归一，不得依赖对象遍历顺序。
- 当前一个 profile-level `vfxRecipe` 可被攻击与神通两个语义视图共同引用，但每个通道仍必须验证该 recipe 与自身模式及同源来源兼容；不能从另一 `setId` 借 recipe。若攻击与神通来自不同 `setId`，规范化结果必须保留两个 phase-scoped 来源包；不能因为当前扁平字段只有一个 `vfxRecipe` 就把攻击源的 recipe 偷渡给神通源，或反向把神通源的 recipe 偷渡给攻击源。
- `fxTags` 应按通道归属保存或在规范化时得到明确通道归属；未能判定来源的 v3 标签记录拒绝，不允许复制到两个通道以“容错”。

## 3.2 v3 bonus 字段规则

| 字段 | 2 件 | 4 件 | 6 件预留 | 语义 |

## 3.3 命名与事实说明

### 命名规则

- 套名、部件名、招式名、神通名均为中文；内部 `profileId`、`attackMode`、`artMode`、`transformId`、recipe ID 只存在于存档、日志或测试。
- 同一条记录的招式名与神通名不得完全相同；名称不能决定伤害、目标、元素或稀有度。
- 名称词池不得使用会承诺未实现机制的词，如“冻结、定身、中毒、领域、护盾、无敌、召唤、反弹、无限分裂”等，除非未来另有已实现 handler、测试与批准。

### 4 件说明最小格式

```text
4件：{数值事实}；
攻击【{招式中文名}】：{真实攻击行为句}；
神通【{神通中文名}】：{真实神通行为句}；
联动：{若有，写批准的首中事实句；若无，不写隐藏效果}。
```

联动事实句必须字面准确：

- 飞剑：`首个有效命中后产生两把子剑，各按父飞剑伤害倍率的0.4结算；联动冷却0.8秒，子剑不会再次触发。`
- 巨剑：`首个有效命中后追加一枚火弹，按父巨剑伤害倍率的0.4结算；联动冷却1.2秒。`
- 大庚组合：不得出现任何分裂或追加火弹句，只说明大庚剑阵真实行为。

## 3.4 VFX、`fxTags` 与同源规则

### 正式 recipe 白名单

当前仍只允许：

- `sword-comet`：飞剑攻击、剑气／大庚阶段的剑形表现。
- `frost-bloom`：玄冰爆发的环状／冰白表现。
- `thunder-sigil`：雷链与雷光的符印／折线表现。
- `giant-crest`：巨剑与其神通阶段的大焦点表现。

首中联动不增加 `split-sword`、`sub-sword`、`firebolt-link` 或其他新 recipe；不使用 `field`。

### 同源与分流

1. 攻击通道的 `vfxRecipe`、攻击标签与攻击联动随攻击通道胜出源绑定。
2. 神通通道的 `vfxRecipe`、神通标签随神通通道胜出源绑定。
3. 攻击与神通来自不同 `setId` 时，可以各自使用不同 recipe；不能让攻击借神通的 recipe，也不能让神通借攻击的联动。
4. 同一标签在同一通道重复出现时去重；互斥标签按注册表拒绝或稳定抑制低优先级项，并必须留下可诊断原因。
5. 未知 `fxTags`／未知 recipe：新生成时拒绝；旧存档读取按兼容策略隔离或忽略，不静默开启未知玩法。
6. VFX 缺资源、未注册动画、性能裁剪或无障碍降级只影响表现，不改变父攻击、子剑、火弹、伤害、冷却、目标或掉落。

### 表现步骤限制

正式步骤仅为 `rune | blade | burst | charge | hit`；`field` 不属于本轮。首中联动的表现只能挂接真实父／子对象已有的起手、载体或命中锚点：

- 飞剑分裂最多表现父剑之外 2 个真实子剑；先裁剪余像与装饰火花，不画虚假路径。
- 巨剑火弹最多表现 1 个真实火弹及必要短启动／命中确认；不增加第二个屏幕级焦点、全屏闪白或地面领域。
- 若没有可验证的子剑／火弹对象，跳过附加 VFX，保留原攻击和静态兜底。

### 3.5.1 Palette V1 身份、资格与确定性

Palette V1 是随机套装的**纯表现身份**，不产生伤害、目标、冷却、输入、掉落、件数、属性、联动资格或任何新的战斗机制。当前工程的 resolver 已落盘于 `src/palette-v1.ts`；它只在合格 v3 记录上派生，且不重新生成套装、不重掷词池、不读取运行时随机状态。该源码事实不等于浏览器实例已播放或 QA 已通过。

| 项 | 当前源码事实／合同边界 |
|---|---|
| 固定版本选择器 | `PALETTE_V1_ALGORITHM_VERSION = 'palette-v1'`；它是 resolver 的版本锁，不要求新增持久化字段。 |
| 合格来源 | 仅 `schemaVersion = 3`、`generation.generatorVersion = 2`，且 `generation.identity`、`generation.theme`、`record.set.id`、调用方 `setId/transformId` 与该记录 4 件 bonus 可交叉匹配的动态记录。静态正式套、测试套、schema v2、无 schema legacy、未知／损坏／隔离记录不进入 Palette V1。 |
| 实际身份键 | `palette-v1|identity.setId|identity.profileId|identity.transformId|generation.theme`；该 key 是当前 Palette V1 的唯一派生输入文本。 |
| 家族选择 | `FNV-1a-32(identityKey) mod 8`；哈希按无符号 32 位结果取模。当前为 **8 个受控 family**，其顺序与色值由 `src/palette-v1.ts` 固定。 |
| 禁止熵源 | 不使用 `Math.random`、时间、帧号、对象／装备遍历顺序、当前场景、设备、网络、粒子状态、播放帧或未持久化临时 ID。 |
| 稳定结果 | 相同的已落盘身份字段得到同一 `identityKey` 与同一受控 family；读档、重进场景、重复施放或表现降级不应改变该派生结果。浏览器侧的实际观察仍待签收。 |
| 后续版本 | 未来如需 Palette V2，必须使用不同版本选择器、独立映射、单独迁移与验收；不得把 V2 规则追溯替换 Palette V1，也不得借此改变 v2／legacy 或静态套视觉。 |

Palette V1 的“纯派生”不等于以 `seed` 重新生成记录：读取时以已落盘的 `generation.identity` 与 `generation.theme` 为事实源。若资格或交叉匹配失败，源码返回**无 Palette V1 覆盖**，并沿用既有固定色／兼容路径；不得猜测一套新颜色。

### 3.5.3 攻击／神通独立来源与同源着色

Palette V1 完全服从本文件 2.2 的独立通道解析，不创建“整套混穿后的第三种综合色”。每个通道先选出既有的能力来源，再由该**同一个来源**决定该通道是否具有 Palette V1 及其具体色板：

| 表现阶段 | 色板来源 | 硬规则 |
|---|---|---|
| 普通攻击、攻击阶段 VFX | 胜出的**攻击通道来源** | 仅当攻击来源本身为合格 v3／generator v2 动态记录时，使用该来源的 Palette V1；不得从同套未胜出的神通、另一 `setId`、装备顺序或全局主题借色。 |
| 神通、神通阶段 VFX | 胜出的**神通通道来源** | 仅当神通来源本身为合格 v3／generator v2 动态记录时，使用该来源的 Palette V1；不得读取攻击来源颜色来覆盖神通。 |
| 攻击首中联动与其 VFX | 触发该联动的**攻击通道来源** | 飞剑子剑与巨剑首中火弹继承父攻击的同一 Palette V1 色彩角色；绝不改用同时胜出的神通色板，也不从 `dageng` 取得颜色。 |
| 无 Palette V1 的来源 | 该来源既有表现路径 | 静态／测试套、schema v2、legacy、未知、损坏或来源无法判定时，保持原有表现；不得用邻近动态套的颜色“补齐”。 |

因此，A 套 4 件攻击 + B 套 4 件神通时，攻击仅可使用 A 的 Palette V1，神通仅可使用 B 的 Palette V1；A 的飞剑／巨剑首中联动也仅继承 A 的攻击色。即使 A 与 B 恰好解析到同一家族，也必须保留各自来源审计，不能以颜色相同推断同源或共享联动。

### 3.5.4 `dageng` 着色与阵法可辨识性

`dageng` 不是 Palette V1 的禁区：当**胜出神通通道来源**是合格 v3／generator v2 动态套装时，大庚剑阵可以使用该来源的随机套色。此许可只改变既有阵法表现的允许色彩角色，不能改变大庚的机制、范围、目标、剑数、节奏、伤害、冷却或本文件既定的首中联动禁配。

为避免随机色掩盖阵法身份，`dageng` 必须同时满足：

- 保留既有阵法的环形／分批剑阵拓扑、符印／剑形轮廓、出现顺序、方向和时序；不得以色彩替代这些非色彩辨识线索。
- `highlight` 与 `darkOutline` 继续承担高亮锚点和背景分离；`primary` 只能作用于既有外缘、剑光与轨迹层。不得把整片剑阵抹成无轮廓的同色雾、领域或全屏闪光。
- `dageng` 仍依本文件 2.3／2.4 的硬禁配解析为首中联动 `none`。随机套着色不构成飞剑分裂或巨剑火弹的资格，也不为其创建对象。
- 若对应序列帧、色层或对比度无法确认，降级为原有可辨识的阵法表现；宁可不显示 Palette V1 覆盖，也不得以缺帧颜色拼接出误导性的阵法。

### 3.5.6 四件生成与六件预留不变

Palette V1 是**套装级视觉派生**，不是新部件、新掉落、新槽位或新能力阶梯。新动态随机套装仍固定生成 `weapon/head/armor/boots` 四件；它们共享该套已派生的 Palette V1 身份，但不会因为着色而创建 `charm1`／`charm2`、第 5／第 6 件、6 件 bonus、饰品掉落或 6 件 UI。

未来若仅为夹具验证而出现合法 `count = 6`／六槽预留记录，其 Palette V1 仍必须从同一已落盘 set 身份纯派生，不得另掷颜色、添加颜色专属机制或改变本文件 3.6 的六件边界。本轮生成器、掉落、玩家 UI 与平衡范围仍不得产生该路径。

## 3.6 真实六槽与六件预留合同

### 真实槽位

本项目真实装备槽只有六个：

| `SlotKey` | 玩家名称 | `ItemSlot` 映射 |
|---|---|---|
| `weapon` | 武器 | `weapon` |
| `head` | 头部 | `head` |
| `armor` | 衣甲 | `armor` |
| `boots` | 靴子 | `boots` |
| `charm1` | 饰品一 | `charm` |
| `charm2` | 饰品二 | `charm` |

硬规则：

- `setPieceCount` 只读取这六个已知 `SlotKey`；未知 key 不计数、不参与数值、不触发能力，不得静默映射到已知槽。
- 当前 PRS 生成器只物化前四槽；`charm1`、`charm2` 不属于本轮随机生成结果。
- 本轮不新增饰品基座、饰品掉落、饰品 UI、饰品词缀或法宝槽。

### 六件合同的预留边界

- 未来六件套的 6 个 `pieces` 必须一一对应六个真实槽，最后两个位置只能是 `charm1/charm2`；不得借用不存在的第七槽。
- 未来 `count = 6` 行可以同时声明数值、攻击通道或神通通道，但必须满足与 4 件相同的分流、同源、禁配与严格校验规则。
- 6 件能力优先于同一通道的 4 件能力；不同 `setId` 仍按通道独立选胜出源。多 `setId` 的数值阶梯继续相加。
- 本轮只验证：六槽可数、未知槽隔离、`count=6` 能力门槛与优先级边界。不得生成、掉落、展示或平衡签收任何六件随机内容。
- 六件预留不改变当前随机套装固定四件的事实，也不授权把现有四件记录补写成六件。

# 第四节｜数值、公式与经济边界

## 4.1 数值聚合：多 `setId` 独立叠加

有效件数按每个 `setId` 独立计算：

```text
validCount(setId) =
  已知六槽中，装备实例 setId 等于该 setId 且槽位合法的件数
```

数值修饰聚合为：

```text
Mods_total[k]
  = 装备基座与强化[k]
  + 装备词缀[k]
  + Σ_setId Σ_bonus( bonus.count ≤ validCount(setId) ) bonus.mods[k]
  + 心法[k]
  + 天赋[k]
```

- 每个 `setId` 的 2／4／6 数值行独立判断、独立相加、独立卸除。
- 一个套装的 `mods` 不得覆盖另一个套装同名键；同名键是加法，不是后写覆盖。
- 能力通道不自动转成数值；只有明确写在 `mods` 中的数值才进入上述公式。
- 4 件能力的攻击与神通可以来自不同套装；这不改变数值独立叠加。
- 未知槽、未知 `setId`、静态碰撞记录或被隔离记录不进入聚合。

## 4.2 既有伤害与神通公式

基础伤害管线保持不变：

```text
D = max(1, round(A × M × C × R − DEF))

A   = 当前攻击（含装备、词缀、心法、天赋与有效套装 Mods）
M   = 当前攻击或神通的既有倍率
C   = 会心倍率；非会心 1，会心 1.6
R   = 随机浮动 [0.90, 1.10]
DEF = 目标防御
D   = 最终伤害，单位：点
```

神通冷却保持：

```text
CD_final = CD_base × (1 − cdPct)
```

其中 `CD_base` 为 profile 的固定神通基础冷却，`cdPct` 沿用最终属性层上限。

### 联动伤害公式

联动只增加有限的投射物事件；新增倍率是相对父攻击事件的唯一新增倍率：

```text
D_child = 既有伤害管线(父攻击事件的有效倍率 × 0.4)
```

- 飞剑的两把子剑分别以 `0.4` 进入既有管线；每把是独立命中事件，不能把两把合成一次虚拟爆发。
- 巨剑追加的一枚火弹以父巨剑有效倍率 `×0.4` 进入既有火弹对象／碰撞管线。
- 会心、随机浮动、防御、保底 1 等既有结算是否按对象事件执行，必须沿用当前攻击对象的真实结算路径；本轮不新增第二个伤害乘区。
- VFX、`procedural_vfx`、recipe、标签、名称均不进入伤害公式。

### 联动冷却

| 联动 | 基础 CD | 单位 | 是否为神通 CD | 是否受 `cdPct` 影响 |
|---|---:|---|---|---|
| 飞剑首中分裂 | 800 | ms | 否 | 否；固定机制冷却 |
| 巨剑首中火弹 | 1200 | ms | 否 | 否；固定机制冷却 |

这样可避免 2 件 `cdPct`、神通冷却与首中联动叠成不可控的隐藏高频收益。若未来要改变该决定，必须更新本 GDD、预算表、模拟器与验收夹具，不得由工程自行套用神通 CD。

## 4.3 数值限制与预算状态

### 本轮硬限制（可直接验收）

| 项 | 硬限制 |
|---|---|
| `seed` | 32 位无符号整数：`0 ≤ seed ≤ 0xffffffff`。 |
| `sequence` | 正整数；`set_dyN`、四个基座 ID 与 generation 必须一致。 |
| 生成件数 | 固定 4；`pieces.length = 4`、`bases.length = 4`，槽位恰为前四槽。 |
| bonus 阶梯 | 新生成只写 `count = 2` 与 `count = 4`；`count = 6` 只允许预留夹具。 |
| 2 件 Mods | 只能使用已注册 `ModKey`；当前生成结构最多 2 个不同键，不得出现能力字段。 |
| 4 件 Mods | 只能使用已注册 `ModKey`；沿用当前生成结构的有限键数，不得借此产生新乘区。 |
| 数值合法性 | 所有数值必须为有限数、非 NaN／Infinity；百分比与冷却不得为负；重复键不得在同一 bonus 内覆盖。 |
| 联动产物 | 飞剑恰 2 子剑、每把 `0.4`；巨剑恰 1 火弹、`0.4`；不可额外复制。 |
| 联动 CD | 只能为 800 ms／1200 ms，整数比较；不能为 0、负数或由显示层另行计时。 |
| profile 神通 | `sword_fan 1.60/7000ms`、`fire_rain 1.20/9000ms`、`thunder_strike 1.40/12000ms`、`dageng 0.45/15000ms`。 |
| 全局属性夹 | 沿用当前最终属性层：`aspd ≤ 0.40`、`lifesteal ≤ 0.35`、`cdPct ≤ 0.50`。 |
| 序号基座成长 | 继续受既有上限约束（当前工程上限为 `tier ≤ 1.50`）；是否重做经济曲线须另立版本，不能回写旧记录。 |

### 数值预算的诚实边界

- 本轮批准的是结构、联动硬参数与安全上限；**每个随机 Mod 的最终概率、跨 2／4 件预算、Build DPS 阈值尚未由模拟器与主理人完成最终签收**。
- 在预算表未签字前，生成器不得扩大现有 `SET_MOD_POOL` 的键集合、数值包络或词条数量；也不得把“示例数值”当作线上平衡承诺。
- `atkPct + skillPct`、会心、吸血、冷却与高覆盖 profile 的组合必须进入后续模拟器；没有样本、难度、楼层、基线与统计结果，不得标记“平衡通过”。
- 平衡风险不阻止本设计合同定义安全边界，但会阻止发布放行；当前发布口径继续为 NO-GO，直到 QA、模拟器与实机证据闭环。

## 4.4 经济边界

- 本轮不新增掉落表、不新增掉落概率、不新增饰品掉落、不改变 Boss／普通怪的资源循环。
- 动态套装达到既有目录上限后继续优先补齐已有套装部件；不因 v3 而无限生成新记录。
- 4 件随机套装的部件掉落继续走既有动态掉落入口；生成器不会因为“首中联动”额外掉落子剑、火弹、材料或饰品。
- 未来六件套经济必须另行设计；本轮不得用六槽预留推导六件掉落概率或图鉴奖励。

# 第五节｜边缘情况、失败回退与反主导策略

## 5.1 生成与 ID 边缘情况

| 情况 | 合同规则 |
|---|---|
| 同一 `seed + sequence + existingCatalog` 重跑 | 完整语义深等；不受时间、全局随机或对象顺序影响。 |
| 稀疏 `set_dyN` | 选择最小未占用正整数；不覆盖旧记录。 |
| 主题池耗尽 | 使用确定性后缀／备用显示语法；不得改写旧套名或产生重复玩家可见名。 |
| 无合法 profile | 显式失败并记录原因；不得默认飞剑。 |
| 生成中途校验失败 | 候选整条丢弃；不将半套注册进 `SETS`／基座表，不部分修补。 |
| 重复注册同一记录 | 结果幂等；不得重复追加基座、标签、监听器或联动状态。 |

## 5.2 通道与混穿边缘情况

| 情况 | 合同规则 |
|---|---|
| A 套 2 件 + B 套 2 件 | 两套数值同时生效；没有 4 件能力。 |
| A 套攻击 4 件 + B 套神通 4 件 | 两通道独立生效；攻击与神通各自携带来源、recipe、标签与联动资格。 |
| 两个攻击通道同为 4 件 | 按稳定 `setId` 码点序选择一个攻击胜出源；不把两个攻击模式叠成新模式。 |
| 一个套装 6 件预留 + 另一个套装 4 件 | 仅在未来六槽夹具验证；6 件在同一通道优先，但本轮随机内容不得构造该玩家路径。 |
| 2 件行伪造 `attack/art/linkage/fxTags` | 新记录拒绝；运行时防御性解析不激活能力；合法数值字段可否保留须由记录级兼容策略决定，不能让伪造字段生效。 |
| 一个通道缺能力、另一个通道有能力 | 缺能力通道独立回退；不从另一通道借模式、名称或 recipe。 |
| 同源标签重复 | 去重；不重复触发监听或联动。 |
| 互斥标签冲突 | 按注册表诊断并拒绝／抑制低优先级项；不得静默同时开启。 |

## 5.3 首中联动边缘情况

| 情况 | 飞剑规则 | 巨剑规则 |
|---|---|---|
| 挥空／撞墙 | 不触发、不占 CD | 不触发、不占 CD |
| 命中死亡目标 | 不算有效首中 | 不算有效首中 |
| 同一父体再次命中 | 父体首中锁存后不再申请 | 同一施放只申请一次 |
| 子剑／追加火弹命中 | 不可成为同类联动父源 | 不可反向触发新火弹或巨剑联动 |
| 冷却内再次合格命中 | 只执行原攻击，不追加联动 | 只执行原巨剑，不追加火弹 |
| 恰好达到 CD 边界 | `elapsed >= 800 ms` 才可触发 | `elapsed >= 1200 ms` 才可触发 |
| 同帧多父体 | 事件序号第一者消费资格，其余受 CD 抑制 | 同一次施放只保留一个权威首中 |
| 卸下套装／换胜出源 | 立即取消旧来源的后续资格；不让旧对象带出幽灵子体／火弹 | 同左 |
| 场景重载／存档重载 | 联动瞬时锁存与冷却不落盘；重新进入场景从零开始 | 同左 |
| `dageng` 神通胜出 | 强制 `none`，即使攻击是飞剑 | 强制 `none`，即使攻击是巨剑 |

## 5.4 槽位、存档与异常边界

| 情况 | 规则 |
|---|---|
| `equipment` 出现未知 key | 忽略该 key；不计数、不聚合、不路由、不触发 VFX／联动；不得静默映射。 |
| 六槽中出现重复实例或同一基座占多个槽 | 由装备／存档规范化拒绝或隔离；不能借重复对象凑 4／6 件。 |
| 动态 ID 与静态 `SETS`／`ITEM_BASE_MAP` 碰撞 | 隔离动态记录；绝不覆盖官方／测试内容。 |
| schema v3 的 generation、set、bases 交叉不一致 | 整条 v3 记录隔离；不重掷、不局部修复。 |
| VFX recipe 缺资源 | 跳过附加表现，保留原攻击、真实投射物、伤害与冷却。 |
| 未知 recipe／未知 linkage | 新记录拒绝；旧记录按版本路径隔离或忽略，不能执行未知行为。 |
| 保存过程中已有 v2／legacy | 维持原语义；不得因保存而重新抽取名字、数值或 profile。 |

## 5.5 反主导策略

1. **大庚让位于可读性与高覆盖预算**：`dageng` 一律禁首中联动，避免 72 道剑气再叠追加投射物。
2. **联动只给一个攻击通道**：一套记录最多一条联动配方，且只由攻击通道胜出源拥有。
3. **数值与能力分离**：多套 2 件数值可以叠加，但不能因为数值叠加而复制能力或监听器。
4. **VFX 不算强度**：recipe、`fxTags`、灵光、命中确认不进入伤害／目标／冷却公式。
5. **控制认知负担**：联动自动触发，不增加第三按钮；玩家只需理解现有攻击键、神通键与事实说明。
6. **经济不膨胀**：固定四件生成、既有动态上限、无饰品／六件掉落；序号成长若导致通胀，另立数值版本处理。
7. **旧物不漂移**：旧 v2／legacy 不获得追溯式新联动，避免玩家已获得物品的强度和玩法突变。

## 6.2 推荐信息层级

```text
【青元套】 4/4
2件：{数值事实}
攻击：{招式中文名}——{真实攻击行为}
```

## 6.3 无障碍与 VFX 可读性

- 机制识别至少同时依赖形状／方向／时序与中文标签中的两种，不依赖单一颜色。

- HUD 与既有按钮继续遵循移动端最小 `44×44 CSS px` 点击区域；本轮不增加按钮，所以不扩大输入负担。
- 不使用 `field`、持续闪烁、全屏闪白或颜色单独编码来暗示联动。

## 6.4 玩家文案禁用与事实句

### 可用事实句

- `飞剑首中后分出两把子剑，各按父飞剑伤害倍率的0.4结算；0.8秒内不会再次触发，子剑不会递归分裂。`

- `大庚剑阵不启用首中联动。`

```text
冻结、定身、中毒、领域、持续伤害、召唤、反弹、护盾、无敌、聚怪、拖拽、
延迟伤害、额外爆炸伤害、无限穿透、无限分裂、自动刷新神通、额外资源
```

除非未来另有完整 handler、白名单、模拟器、测试与设计审批，不得把上述词写入当前 PRS 机制说明。

### 纯逻辑边界

首中资格、来源序号、冷却、子体封锁、数量与倍率应在可单测的纯逻辑层裁定；Phaser／场景层只负责：

1. 创建已被逻辑批准的对象；
2. 将对象渲染到已有 route；
3. 将真实命中回传给既有伤害管线；
4. 在资源缺失时安全跳过附加表现。

禁止让场景 VFX 回调、坐标启发式或动画完成事件反向决定游戏命中。

## 7.2 存档 v3 与兼容策略

### 新记录

- 新生成动态套装写 `schemaVersion = 3` 与 `generation.generatorVersion = 2`。
- `set`、`bases`、`generation` 完整落盘；读取以已落盘结果为权威，不因 profile 权重、词池、数值预算或 VFX 资源更新而重掷。
- `seed` 供审计、重放与测试；不是读取时重新生成的唯一事实源。

### schema v2 记录

- 识别 `schemaVersion = 2` 的旧动态记录，走 v2 严格验证与兼容适配。
- 保留其原有 `set/bases/generation`、模式、名称、数值与标签语义；不得补发 v3 联动，不得把旧扁平字段猜成新的通道能力。
- 若旧记录只有一个组合能力源，兼容视图可以同时提供已有攻击／神通字段，但不能把不存在的字段扩展为新的 4／6 能力。
- v2 记录可继续装备、战斗、保存与读取；迁移若发生，必须是字段复制与语义保持，不得调用新生成器。

### legacy 记录

- **只有完全不存在 `schemaVersion` 属性**的 `{set, bases}` 动态记录才走 legacy 路径；显式 `schemaVersion: undefined`、未知版本或残缺 schema 不得降级成 legacy。
- legacy 记录只要结构、ID、槽位与已实现模式安全，即按旧语义继续运行；没有 seed 的记录不凭空补造 seed，不重掷名称或数值。
- legacy 中的旧标签按旧兼容路径处理；不能把旧 `sword_split`／`fire_burst` 字面值自动升级成 v3 的两条受控 recipe，也不能让未知标签进入新联动。

### 版本隔离

- `schemaVersion = 3` 不等同 `SAVE_VERSION`。当前源码读到顶层 `SAVE_VERSION = 6`；未来是否需要提升，取决于顶层存档结构是否改变。工程必须在迁移设计中明确，不可只改任一版本常量。
- 未知高版本记录隔离或安全回退，不能删除字段后伪装成 legacy。
- 任何迁移都必须保留旧记录的已落盘战斗结果；若无法无损映射，隔离该条动态记录并保留其余存档。
- 静态官方／测试 ID、基座 ID 与动态 ID 的碰撞保护始终优先于兼容加载。

## 7.3 实施顺序建议（交工程／QA，不是本轮执行）

1. **数据契约**：定义 v3 record、channel envelope、linkage registry、recipe／tag registry 与 validator。
2. **数值解析**：先锁六槽白名单与多 `setId` 独立聚合，再接攻击／神通双通道 resolver。
3. **纯逻辑联动**：实现首中事件、来源序号、800／1200 ms 冷却、子体封锁和 `dageng` 禁配；补边界单测。
4. **场景适配**：只渲染真实对象，复用现有投射物／recipe；缺资源只降级表现。
5. **存档迁移**：新增 v3 写入，覆盖 v2／legacy 读取、往返、隔离、重复注册与静态回归。
6. **质量与平衡**：运行默认测试、数据校验、类型检查、标准构建、真机与 Playtest；建立模拟器后再签数值。
