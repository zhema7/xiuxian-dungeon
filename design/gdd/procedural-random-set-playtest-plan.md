# 《修仙与地下城》程序化随机套装（PRS）实机验收与平衡证据计划

> **文档性质**：当前 PRS 的实机验收执行表、结构化 Playtest 脚本与平衡证据采集计划。它为后续用户／QA 实际操作做准备，**不表示任何实机测试、QA 签收、默认并行测试稳定性、标准构建或发布已完成**。  
> **适用候选**：当前 `schemaVersion = 2`／`generatorVersion = 1`；候选版本、提交标识、构建 URL 或安装包信息必须在执行前填写。  
> **当前发布状态**：**NO-GO**。默认并行 Vitest 模块图稳定性、QA 独立签收、标准构建证据、实机烟雾与结构化 Playtest 均为发布前置。  
> **范围边界**：只验当前四个工程已接入家族、四种既有神通模式和四条 `vfxRecipe` 白名单；不把 Task #20 九类独立战斗语法、`vfxPreset/vfxVariant/vfxSeed`、持续领域、BP 门控或新 UI 栏位混入本轮结论。

## 1. 目标、结论口径与执行原则

### 1.1 本计划要回答的问题

1. 当前 PRS 是否能在真机上以**固定 seed**复现四个已接入战斗家族，并以中文说明和受控 VFX 呈现真实行为？
2. 低于 4 件、恰好 4 件、卸下一件、存档重载、重复加载、混穿优先级与旧静态套装是否仍符合当前设计契约？
3. 不同设备上，当前 VFX 是否只作为表现层，既不遮蔽关键操作／信息，也不被误读为额外伤害、控制或状态？
4. 新玩家、中盘玩家、高层玩家能否理解“套装实际改变了什么”，并为后续平衡模拟与设计审批提供可追溯的**体验证据**？

### 1.2 不得从本计划得出的结论

- 不得因本计划已写成或个别试玩通过，宣称 QA PASS、完整 P0 已验收、默认并行 Vitest 已稳定、标准构建已通过、实机测试已完成或发布可放行。
- 不得将当前四家族扩写为 Task #20 的九类独立战斗语法；当前九类目标只列有八个命名候选，第九类尚未定义。
- 不得把“剑域／炎界／雷狱”等诗性名称解释为领域、持续伤害、禁锢、减速、状态或额外结算。
- 不得将 `procedural_vfx + vfxRecipe` 以外的 `vfxPreset`、`vfxVariant`、`vfxSeed`、`resonance`、`readabilityTier`、`field` 步骤或持续领域写成当前验收对象。
- 不得将 Playtest 主观反馈或少量手工战斗结果写成 BP 合规、胜率达标、DPS 平衡或经济健康的结论。

### 1.3 当前验收对象：工程已接入事实

| 项 | 当前边界 | 本计划的验收口径 |
|---|---|---|
| 套装结构 | 武器／头部／衣甲／靴子，2／4 件阶梯 | 重点验证 `<4` 件不覆写、恰好 4 件覆写、卸下一件关闭覆写。 |
| 攻击家族 | 飞剑齐射、玄冰爆发、紫霄雷链、巨剑术 | 每个家族至少完成一条固定 seed 真机路径。 |
| 神通模式 | 剑气纵横、流星火雨、九天神雷、大庚剑阵 | 验证当前 profile 指定神通、中文 `artName` 提示与真实既有行为一致。 |
| VFX | `procedural_vfx + vfxRecipe`；`sword-comet`／`frost-bloom`／`thunder-sigil`／`giant-crest` | 只验 `rune/blade/burst/charge/hit` 的受控表现和安全降级；不验 `field`。 |
| 存档 | schema v2、完整 `set/bases`、seed／sequence、非法记录隔离、legacy 兼容 | 验证普通存取档／重复加载不丢失当前记录或产生可见重复；篡改隔离由 QA 夹具独立复验。 |
| 当前玩家可见信息 | 套名、件数、2／4 件事实说明、套装神通 `artName` 提示 | 不把传承、流派独立栏位、独立灵光名、集齐四件独立提示当作当前预期。 |

## 3. 固定 seed 验收清单

### 3.1 固定 seed 的使用纪律

- 固定 seed 表是**候选验证夹具**，不是掉落概率、平衡权重或跨版本永久承诺。
- 每次执行必须在同一候选上先用自动化／QA harness 确认“seed + sequence + existingCatalog → profile”映射；不同 `generatorVersion`、词池、权重或目录状态下不得沿用旧预期。
- 对应 seed 的实际中文名字可随完整生成流程得出，但验收时须记录其真实生成结果；不要手填假定名称。
- 当前普通 UI 的随机入口若无法输入 seed，不得以自由随机替代。应由 GM、测试入口或 QA harness 注入，无法注入则登记 `BLOCKED`。

## 5. 混穿优先级与静态套回归

### 5.1 混穿优先级

当前规则为：更高件数优先；同件数时按 `setId` 字典序稳定决策；VFX 只跟随实际胜出的攻击／神通覆写。

| 用例 ID | 准备 | 操作与预期 | 证据／限制 |
|---|---|---|---|
| MIX-01 | 一个动态套 4/4 + 另一套不足其覆写阈值 | 动态 4 件套应胜出；不得从低优先级套借用 VFX。 | 常规真机可执行；录屏攻／神通／VFX。 |
| MIX-02 | 两个能同时激活覆写的套装，且件数不同 | 更高件数覆写必须胜出。 | 若普通 UI 无法合规构造，使用既有 QA fixture／harness；不改数据或源码绕过。 |
| MIX-03 | 两个同件数、可同时激活的覆写 | 按 `setId` 字典序稳定决策；攻击、神通与 VFX 保持同一胜出来源。 | 优先 QA fixture／harness，记录构造条件和 resolver 输出。 |
| MIX-04 | MIX-01～03 任何一例 | 保存、重载、再战斗 | 胜出结果不因设备、重载或装备对象遍历顺序漂移。 |

> **执行限制**：当前 PRS 是 4 件结构，且玩家可见普通 UI 未必能无副作用地构造“双动态 4 件同时激活”的场景。无法以正常装备流程构造时，不得伪造玩家路径；将 MIX-02／03 标为 `QA HARNESS REQUIRED`，交由现有 fixture／resolver 测试独立复验。

### 5.2 静态套装回归

每个设备至少任选一套当前静态正式套装；每个候选至少覆盖四套中的全部一次。测试顺序建议在动态套 F-07 后立即进行，以发现注册污染。

| 静态套 | 回归预期 | 证据 |
|---|---|---|
| `set_qm` 青冥剑套 | 原有描述、阈值、攻击／神通／视觉标签不被动态内容改写。 | 套装说明 + 普攻／神通录屏。 |

## 7. 结构化 Playtest：新／中盘／高层各 3 人

### 7.1 招募与伦理边界

- 每组 3 人，共至少 9 人；同一人不可同时占多个分层。
- 参与者使用代号，不在本计划或公开证据中记录真实姓名、联系方式、账号、完整设备标识或其他个人敏感信息。
- 告知参与者：这是测试候选，可能遇到错误、性能问题或存档异常；必须使用测试档，不影响正式存档。
- 每人体验前后由观察者记录；不能由主持人诱导答案或解释机制后再把答案当“自然理解”。

### 7.2 分层定义与任务脚本

| 分层 | 人数 | 入选特征 | 首次任务 | 观察指标 |
|---|---:|---|---|---|
| 新玩家 | 3 | 未接触或极少接触本项目；不熟悉套装覆写术语 | 给定 3/4 与 4/4 同一动态套，30 秒内说出“装备满四件改变了什么”；施放一次套装神通。 | 是否分清招式／神通；能否说出真实行为；是否把诗性名或 VFX 当成额外机制；UI 阅读顺序和困惑点。 |
| 中盘玩家 | 3 | 熟悉装备／套装／掉落循环，但不要求高层优化 | 比较两条不同当前家族 profile 的 4/4 动态套，在给定场景选择愿意补齐哪套并说明理由。 | 是否感知路线差异；是否认为所有套装“只是换名字”；说明能否支持取舍；掉落追求是否清楚。 |
| 高层玩家 | 3 | 有无尽／高层／Build 优化经验 | 体验至少一个大庚组合和一个非大庚组合，在相同候选条件下描述强度感、风险感和是否出现明显单一主导。 | 高覆盖可读性、强度主观感、主导策略信号、性能／操作负担、是否需要数值进一步调查。 |

### 7.3 统一观察提问

**新玩家（先自由回答，再追问）**

1. “你认为这套装在 3/4 和 4/4 时分别改变了什么？”
2. “请用自己的话说明这个招式和这个神通各做什么。”
3. “你认为画面里的额外灵光改变伤害、控制或目标数量了吗？为什么？”
4. “有没有你看不懂、以为会产生额外效果的词？”

**中盘玩家**

1. “在这两套之间，你会先补齐哪套？依据是名称、说明、战斗表现还是数值？”
2. “两条路线是否足够不同？哪一条更适合什么场景？”
3. “你是否会因为看不懂招式／神通实际行为而放弃选择？”
4. “掉到这类套装后，下一步目标是否明确？”

**高层玩家**

1. “哪条组合让你感觉最可能成为唯一最优？请指出具体攻击、神通、词条或覆盖原因。”
2. “大庚／巨剑／雷链等高覆盖组合是否造成画面、输入或性能压力？”
3. “你观察到的强度感是来自实际机制、数值、名称还是 VFX？请分开说明。”
4. “哪些现象需要模拟器验证，而不是凭这次体验直接调数值？”

|---|---|

## 9. 结果分级、升级路径与签收

### 9.1 用例结果定义

| 结果 | 含义 | 发布含义 |
|---|---|---|
| PASS | 该条用例的预期与实际一致，证据完整。 | 只证明该条用例；不自动关闭任何其他门。 |
| CONCERNS | 未阻断当前用例，但存在可读性、性能、样本、设备或设计待决项。 | 维持 NO-GO，直到主理人／QA 明确处置。 |
| FAIL | 行为与当前工程／GDD 事实不一致，或出现回归、串扰、错误机制承诺。 | 依严重度阻断 QA／发布；不得继续把候选描述为通过。 |
| BLOCKED | 设备、seed 注入、构造条件、保存、录屏或候选身份缺失，无法得出结论。 | 不是 PASS；维持 NO-GO 并列入待补资源。 |

### 9.2 缺陷升级规则

| 情况 | 最低等级 | 去向 |
|---|---|---|
| 存档丢失／重掷／重复注册污染／覆盖静态内容 | Blocker | QA + 工程，停止候选发布评估。 |
| `<4` 件错误激活、4 件未激活、卸装残留、攻击／神通／VFX 路由错配 | Critical | QA + 工程；保留 seed、存档和连续录屏。 |
| 中文说明与真实行为不一致、内部 ID 泄露、雷链目标数错误、VFX 误导额外机制 | Major | 设计 + QA；先修说明或实现，禁止用文案掩盖。 |
| 低端设备明显掉帧、VFX 遮挡、iOS 安全区／音频／重载问题 | Major（可因不可玩升 Critical） | QA + 工程 + 美术／UX；按设备和复现频率记录。 |
| 传承／流派／独立灵光栏位未出现 | 不计缺陷 | 当前不在工程已接入范围，记录为未来 UI 需求而非回归。 |

### 9.3 发布签收顺序

1. 执行者完成设备矩阵与结构化 Playtest 的原始证据。
2. QA 独立复验 schema、存档、运行时、静态回归与默认并行测试；不得用本计划的手工结果替代自动化 P0。
3. 工程／发布线完成标准构建与证据归档；如构建环境阻断，按 QA／发布文档记录阻断，不伪装为 PASS。
4. 设计完成平衡证据审阅，明确哪些只是体验信号、哪些进入模拟器任务；未有模拟器与审批前不出平衡 PASS。
5. 主理人汇总所有前置并明确记录 GO；此前一律 **NO-GO**。
